# Best Time to Buy and Sell Stock

## 문제 분석

- `prices[i]` 는 `i` 일의 주가다. **한 번 사서 한 번 파는** 경우의 최대 이익을 구한다.
- 반드시 **사는 날이 파는 날보다 앞서야** 한다. `prices[j] - prices[i]` 에서 `i < j`.
- 이익을 낼 수 없으면 `0` 을 반환한다. 손해 보면서까지 거래하지 않아도 된다.
- 핵심 관찰: **파는 날을 기준으로 생각하면** 답이 단순해진다.
  `j` 일에 판다고 정하면 최선의 매수일은 `0..j-1` 중 **가장 싼 날** 하나뿐이다. 다른 후보를 볼 이유가 없다.

---
## 풀이 고민

### 자료구조/알고리즘 후보
- 선택지 A : 모든 `(i, j)` 쌍을 이중 반복문으로 비교
- 선택지 B : 한 번 순회하면서 "지금까지의 최저가"만 들고 다니기

### 선택지 A 설명

`i < j` 인 모든 쌍을 돌면서 `prices[j] - prices[i]` 의 최댓값을 찾는다.
문제 정의를 그대로 옮긴 형태라 틀릴 여지가 거의 없다.

문제는 비용이다. `O(n^2)` 이고 `prices.length` 가 최대 `10^5` 이므로
비교 횟수가 약 50억 번까지 늘어난다. 시간 초과가 확정이다.

또 하나, 이 방식은 **이미 답에서 탈락한 매수일을 계속 다시 본다.**
`i1 < i2` 이고 `prices[i1] <= prices[i2]` 라면 `i2` 를 매수일로 쓸 이유가 영원히 없는데도 매번 비교한다.

### 선택지 B 설명

선택지 A에서 낭비를 발견한 지점이 그대로 개선점이 된다.
`j` 일에 팔 때 필요한 정보는 `0..j-1` 의 **최솟값 하나**뿐이다. 배열 전체를 다시 볼 필요가 없다.

그래서 값 두 개만 들고 한 번 순회한다.
- `minPrice` : 지금까지 본 가장 싼 가격
- `maxProfit` : 지금까지의 최대 이익

각 날마다
1. `maxProfit = max(maxProfit, prices[i] - minPrice)` — 오늘 팔았을 때의 이익을 후보에 넣고
2. `minPrice = min(minPrice, prices[i])` — 최저가를 갱신한다

`O(n)` 시간, `O(1)` 공간이다.

---
## 최종 결정 및 근거

**선택지 B (한 번 순회 + 최저가 추적) 를 선택했다.**

### 왜 이익 계산이 최저가 갱신보다 먼저인가

순서가 바뀌면 **같은 날 사서 같은 날 파는** 경우가 답에 섞인다.

`minPrice` 를 먼저 갱신하면, 오늘 가격이 최저가일 때 `prices[i] - minPrice == 0` 이 후보로 들어간다.
값이 `0` 이라 대부분의 입력에서는 답이 바뀌지 않지만, 이건 **우연히 안전한 것**이지 논리적으로 옳은 게 아니다.
`i < j` 라는 제약을 코드에서 지키는 자리가 바로 이 두 줄의 순서다.

이익을 먼저 계산하면 `minPrice` 는 항상 **어제까지의** 최저가다. 제약이 코드 구조로 보장된다.

### 왜 `maxProfit` 의 초기값이 0인가

"거래하지 않는다"는 선택지가 항상 존재하고, 그때 이익은 `0` 이다.
주가가 계속 떨어지는 입력(`[7,6,4,3,1]`)에서는 모든 이익 후보가 음수인데,
초기값이 `0` 이므로 `max` 가 자연스럽게 `0` 을 지킨다. 음수 검사 분기가 따로 필요 없다.

### 왜 `minPrice` 초기값이 `prices[0]` 이고 반복이 `i = 1` 부터인가

`prices[0]` 은 팔 수 없는 날이다. 그 앞에 살 수 있는 날이 없기 때문이다.
매수 후보로만 쓰이므로 `minPrice` 의 초기값으로 넣고, 매도 후보는 `i = 1` 부터 본다.
`Integer.MAX_VALUE` 로 초기화하고 `i = 0` 부터 도는 방법도 있지만,
그러면 첫날에 `prices[0] - MAX_VALUE` 라는 큰 음수가 계산돼 오버플로 걱정이 생긴다.

| 기준 | A: 이중 반복문 | B: 한 번 순회 (선택) |
| --- | --- | --- |
| 시간 복잡도 | `O(n^2)` | `O(n)` |
| 공간 복잡도 | `O(1)` | `O(1)` |
| `n = 10^5` 에서 | 시간 초과 | 통과 |
| 코드 길이 | 짧음 | 짧음 |
| 틀릴 여지 | 거의 없음 | **두 줄의 순서**에 정확성이 걸림 |

## 회고

### 검증

| 입력 | 기댓값 | 결과 |
| --- | --- | --- |
| `[7,1,5,3,6,4]` | 5 | 통과 |
| `[7,6,4,3,1]` | 0 (거래 안 함) | 통과 |
| `[1,2]` | 1 | 통과 |
| `[2,1]` | 0 | 통과 |

### 배운 점

- "사는 날"이 아니라 **"파는 날" 기준으로 뒤집어 보니** 후보가 하나로 줄었다. 기준을 바꾸는 것만으로 `O(n^2)` 이 `O(n)` 이 됐다.
- `i < j` 같은 제약은 조건문으로 검사하는 것보다 **코드 순서로 보장**하는 쪽이 안전하다. 검사는 빠뜨릴 수 있지만 구조는 빠뜨릴 수 없다.
- 초기값 `0` 하나로 "거래하지 않는다"는 선택지를 표현했다. 방문길이에서 빈 칸을 `0` 으로 둔 것과 같은 방식이다 — 특수 케이스를 값으로 흡수하면 분기가 사라진다.
